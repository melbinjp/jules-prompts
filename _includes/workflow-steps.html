The recommended sequence for making any idea real, software or physical, and keeping it working and improving: found it on written reasons, build it in traced changes, take it to production quality, and improve it continuously after launch. Start at the first step for an idea, and at the second for a project that already exists. Each step names when it is done, and the other skills it calls on.

  1. Start from the idea

    Work out what it takes to make the idea happen and how it is paid for. Make the few decisions that are costly to reverse with verified evidence. Make every stage of the pipeline a command a person or an agent can run, and build one thin slice end to end. The ledger it writes gives every later step its reasons. For a project that already exists, write the ledger from what is there.

    Done when the owner has agreed the path and its first step, the ledger passes the trace check, and the walking skeleton has run end to end and been rolled back once.

    Calls on Choose Between Options with Evidence, Act on the Physical World, and Prove It Happened, Map the Architecture, Keep a Project Confidential, Offline First

  2. Make it run from cold

    Dependencies install, the tests run to completion, and nothing reports success while broken, so every later step starts from a baseline rather than an assumption.

    Done when a clean checkout installs and runs its tests with one command, and breaking a step makes that command fail.

    Calls on Isolate Tests from External Services

  3. Choose with evidence, whenever a choice matters

    Compare real options for each consequential choice, including building it and combining several. Use criteria from the goal, back the decision with at least two pieces of evidence (one verified), redo every number, and keep a way out.

    Done when the decision record passes the trace check, and the owner has approved it if it is costly to reverse.

  4. Build in changes that each have a reason

    Every milestone and every request, however vaguely worded, is translated into a measure, verified before and after, built through every layer it touches, and traced to the goal, with nothing left behind.

    Done when every claim in the request is accounted for, every commit has its Serves and Verified lines, the measure moved, and nothing is left detached.

    Calls on Scope a Vague Issue, Fix a Bug, Failing Test First, Verify a Database Migration Before It Meets Real Data, Run the Error Paths, Act on the Physical World, and Prove It Happened

    repeat as needed

  5. Take it to production quality

    Write the bar, then close the gap in order of what it costs the people who use it: nothing lost, the core job on every platform, finished to use, nothing it does not need. Every item ends as holds, broken or skipped.

    Done when every row of the bar holds, or is broken or skipped with its reason and its next step in the plan.

    Calls on Security Review of Agent-Written Code, Run the Error Paths, Prove the Documentation Against the Code, Map the Architecture, Act on the Physical World, and Prove It Happened

    repeat as needed

  6. Review what the agent produced

    Check each pull request against the claims it makes about itself, and break the code under every new test to see it go red.

    Done when every claim the pull request makes is checked, and every new test has been seen to fail.

    Calls on QA the Tests an Agent Wrote, Prove the Fix by Making It Fail, Repair a Pipeline That Is Green Without Checking Anything

    repeat as needed

  7. Keep it on course and improving, for good

    At every milestone and continuously after launch: take every measure again from its source, switch routes where a course change fired, remove what no longer serves the goal, run the pipeline both ways, and rank the next improvements. The project continues, adjusts, re-routes or grows; it is never left half-done.

    Done when every measure was taken from its source this run, the next improvements are ranked into the next milestone, and the ledger is committed. Then it starts again.

    Calls on Change a Project with a Reason, Choose Between Options with Evidence, Update Dependencies, Keep a Project Confidential, Offline First

    repeat as needed

  8. Keep it current

    Update dependencies in small, verified steps, so staying current never becomes a rewrite.

    Done when each update is its own verified commit, and the suite passes on the new versions.
